# Tadbirkorlik asoslari

The new mobile-first TerDU learning environment. All 15 original presentations, quizzes, exercises, PDF/video materials, accounts, academic scores, teacher controls and game data remain available. Existing Realtime Database records remain authoritative and are never deleted or reset. Approved migration creates private linked profile/progress snapshots in Firestore.

## Run locally

Use Node.js 22 or newer. Run these commands from this folder:

```bash
npm ci
npm run dev:demo
```

Open http://localhost:3000. The local demo role selector provides separate student, teacher, and administrator accounts. Demo changes are saved in `.studyquest-demo/`; deleting that folder resets only the local demonstration. Demo presentation frames use isolated browser storage and block live Firebase requests. **Demo authentication is disabled in production and on Vercel.**

For Firebase-backed development, copy `.env.example` to `.env.local`, supply your own configuration, and run `npm run dev`. Without backend credentials the application exposes the existing presentation site and clearly disables the new platform services.

- Course catalog with **Tadbirkorlik asoslari → 15 numbered topics**, course progress, module filters, and course/topic search.

- Email/password, password reset, Google sign-in, and a bridge to existing TerDU accounts. University students retain the original approval and lesson-access checks. New email accounts are independent learners by default.
- Server-graded choice, true/false, matching, and accepted-answer quizzes; randomized question order, attempt limits, time limits, feedback settings, and history.
- **Points come only from presentations and extra tasks** — no XP is shown or awarded. Each topic gives up to 100 points (30 slides + 20 reading time + 50 test); teacher marks and live-quiz prizes add extra points. Badges and learning streaks remain as encouragement.
- **Daily and overall rankings**: the top ten rows are coloured, the rest plain; each row shows the place, name, group and points, with an empty avatar silhouette (avatars will be given later as rewards). A card above the list shows the student's own place, points and the gap to the next place; group chips filter the list. The daily ranking counts points earned since 00:00 Tashkent time: the original engine records each student's day-start total (`students/<id>/dd`, `d0`). Independent learners remain outside university rankings.
- Teacher tools for subjects, courses, modules, lessons, quizzes, material uploads, enrollment, classes, achievements, analytics, and CSV reports. Administrator tools manage roles, blocking and platform settings.
- Memory, vocabulary, arithmetic, and typing practice. Quiz Battle opens a server-graded timed quiz; existing multiplayer class games use the new native Game Arena surface.
- **Site manager (back office):** **Admin → 🛠 Site manager** is the administrator's starting page — one card per task, each with a one-line explanation, so the site is run without a developer: ✏️ texts and pictures, 📝 topic tests, ⚡ live quiz, 🎭 avatars and the avatar library, 📢 announcements, 🛍️ the second box (offers), plus shortcuts to topic access, students and grades, platform settings and the classic panel. Its data lives in the original database under `site/*`, which has no client rule at all: only the server (Admin SDK) reads and writes it, and pages receive it through cached API responses (no Firestore quota).
- **Click-to-edit texts and pictures:** **Admin → 🛠 Site manager → ✏️ Texts and images → Start editing** turns on an edit bar for the administrator: clicking any text (headings, buttons, menu items, hints, even slide text inside presentations) opens a small window with the original and a field for the new text; clicking a picture (e.g. the logo) lets them upload a replacement, shrunk in the browser to at most 1600 px. «Browse pages» pauses editing to move around; «Done» ends it. The same text changes everywhere at once, per language; numbers and symbols cannot be changed this way. Changes live in `site/texts/<key>` and `site/images/<key>` (picture bytes in `site/blob/<key>`, only real PNG/JPEG/WEBP/GIF, no SVG), reach every page through `/api/site/content` (CDN cache ~30 s) and are applied as plain text, never HTML; pictures are served from `/api/site/img/<key>?v=…` with a one-year immutable cache. The list in the same section shows every change with who made it and when, edits it inline, replaces texts that cannot be clicked (e.g. pop-up messages) and restores anything to the original. `next.config.ts` keeps all other API responses `private, no-store`.
- **Topic tests editable in the browser:** **Admin → 🛠 Site manager → 📝 Topic tests** lists the 13 topics that end with a test (topics 4 and 5 use a crossword or tasks). The editor starts from the original questions — `scripts/sync-legacy.mjs` extracts each presentation's `Q` array into `public/legacy/quiz/<topic>.json` at build time — and lets the administrator change the text, the four answers and the correct one, switch a question to a typed answer, reorder, and restore one question or the whole test. The number of questions stays fixed because the 50 test points depend on it. Saved tests go to `site/quiz/<topic>`; the presentation copy loads `/api/site/quiz?t=<topic>` in its `<head>` (cached ~30 s at the CDN), which sets `window.SQ_Q` before the original engine runs (`var Q=window.SQ_Q||[…]`); the English copy is switched off for an edited test and the in-progress attempt key includes the version, so an older attempt never mixes with new questions. Only `<b>`, `<i>`, `<u>`, `<sub>`, `<sup>` and `<br>` survive in question text.
- **Live quiz restored in the new site:** the original live quiz (Kahoot-style, `kahoot/*`) is read and run by the server. From 20 minutes before the start until the end, a small «⚡ Live quiz» card (anyone may close it) and the side announcements box lead into the game (`#arena/play/live`, typing race `#arena/play/yozuv`). Administrators manage it under **Admin → 🛠 Site manager → ⚡ Live quiz**: the daily automatic game (time, number of questions, seconds per question, sections), the upcoming games (cancel or stop any of them), a hand-picked game (date, time, note, questions), the question bank (add, edit, delete, many at once from text, JSON import/export) and recent results. The server writes exactly the original format (`lib/live-quiz.ts` mirrors `khMakeGame`, `khScore`, `yzScore`, `khParse` and `khQid`; a unit test runs the originals side by side), finalizes finished games so winners' points still reach the overall score, and tops the 14-day schedule up by itself at most every 6 hours (lock `site/locks/liveAuto`). Live typing races are still set up in the classic panel.
- **Announcements box:** a permanent square box under «Students' chat» in the side menu (on phones, at the top of the home page) shows the next live quiz and the administrator's announcements, switching every 10 seconds (paused on hover, with the pause button or while one is open). A long announcement is shortened in the box (it fades out with a «Read all» hint); clicking it opens the full text, title, date and link in a window (Esc, «×» or a click outside closes it). Announcements may be up to 1500 characters. **New announcements open big:** when the administrator leaves «Show it to everyone in a big window» on (the default), every signed-in user who opens the site sees the announcement in a large window (title, full text, date, link) until they press «Read»; after that it only stays in the announcements box and never pops up again — on any device, because the read marks live on the server in `site/newsSeen/<user>/<id>` (guests: in the browser). «×» or Esc closes it for now only, so it comes back on the next visit. Several unread announcements come one after another, newest first; the author never gets their own, and nothing pops up inside arena games. Administrators post and delete announcements (title, text, optional link and end date) under **Admin → 🛠 Site manager → 📢 Announcements**; records live in `meta/news/<id>`, written only by the server. The box is built to catch the eye: a shimmering gold-pink-violet frame, a short pop and glow when the site opens, a passing light sweep, a blinking dot and a «NEW» tag on announcements younger than three days (all motion is off when the device asks for reduced motion).
- **Second box (offers):** at the bottom of the side menu, in place of the former «Current topic» card (that information is already on the home page; on phones the box sits on the home page under the announcements), a warm-coloured box advertises products, courses and grant programmes. Each offer has a kind (product, course, grant programme or notice), a title, a short text, an optional link with its own button label, an optional picture and an optional end date; offers switch every 10 seconds, clicking one opens its full text with the picture and button (texts up to 1000 characters) and new ones carry a «NEW» tag. Administrators manage them with a live preview under **Admin → 🛠 Site manager → 🛍️ Second box (offers)** (or the «+» on the box). Records live in `site/promo/<id>` and pictures in `site/blob/pr-<id>` (server-only, picture type checked from its bytes); they reach pages in the same cached `view=news` response as the announcements. With no offers, students do not see the box.
- **Message the admin — a Telegram-style chat:** on the chat page («Message the admin» tab) a student or teacher and the administrator talk in one conversation: message bubbles grouped by day, the sender's name once per group, time and ticks (✓ sent, ✓✓ read by the administrator), Enter to send and Shift+Enter for a new line. Any message can be answered with ↩ — the reply shows a quote of that message, and clicking the quote scrolls to the original and highlights it. Administrators and teachers see the conversations on the left (unread count, «waiting for a reply» filter; opening one marks it read) and the chosen conversation on the right; on phones the list and the conversation take turns. Both sides refresh every 10 seconds while the page is visible. Every message is deleted automatically 7 days after it was written (old records are removed from the database whenever a conversation is read). Data: `support/<owner>/<message>` in the original Realtime Database, one record per message with `from` (user/staff) and an optional `re` quote; older records with an embedded `reply` are shown as two messages. Up to 20 messages per 10 minutes per student.
- **Avatars as rewards:** students in places 1–10 of the overall ranking, and students the administrator allows, choose a character from the avatar library (10 characters in `public/avatars/`). Each avatar belongs to one student at a time; a student who drops out of the top 10 without permission loses it and others may take it. The avatar stands on the right of the student's ranking row and on the home page card in place of the topic picture; an empty silhouette opens the library. Students can suggest new avatars (sent to «Message the admin» with the 🎭 category). Administrators allow students and free avatars under **Admin → 🛠 Site manager → 🎭 Avatars**, where the library itself is managed too: add a new avatar (picture + name in up to three languages + source), rename any avatar, replace or restore its picture, hide it (a hidden avatar cannot be chosen and disappears from its owner) or delete one you added. Uploaded pictures are prepared in the browser like the 10 built-in ones: a white (or other plain) background is found from the picture's edges and made transparent (white areas inside the character stay), edge pixels are freed from the background colour so no white halo remains, the character is trimmed and the longest side is limited to 480 px (`lib/avatar-cutout.ts`, `components/avatar-prep.ts`). Busy photo backgrounds are left untouched with a warning; the option can be switched off, and «🪄 Clean the background» fixes a picture uploaded earlier. The library is the 10 built-in characters plus `site/avatars/<id>` (pictures in `site/blob/av-<id>`), merged on the server (`lib/server/avatar-library.ts`, cached 30 s) and sent with the ranking, so the picker, ranking rows and home card all use it. Records: `meta/avatars/own/<avatar>` and `meta/avatars/allow/<student>`, written only by the server in a transaction. Character images belong to their copyright holders (see `public/avatars/NOTICE.txt`).
- **Online now in the arena:** the Games page lists classmates who are in the arena (free or playing). Press _Invite_, pick Business, Draughts, Chess, Connect Four or Puzzle duel, and the classmate gets an accept/decline window; once accepted, the game starts for both. It shares the original arena's records (`arena/on`, `arena/inv`, `arena/rooms`), so players on the new page and in the original arena see and invite each other.
- **💼 «Biznes» (Business) game:** a 12-month entrepreneurship duel in the arena (`#arena/biznes`). Both players open the same business with the same 100 mln so‘m: a **somsa bakery** (production — unsold portions are wasted), a **gadget shop** (retail — stock carries over and 5% of it ages every month, cheap goods come back as returns) or a **learning centre** (a service — satisfied students stay for months, premium means smaller groups). **Round 0 is a business plan:** location (by the university, by the central bazaar or inside a neighbourhood — rent versus closeness to each customer group), equipment (new, used and cheaper but prone to breakdowns, or leased), team size and a launch campaign; the first month’s rent is paid up front and the rest is working capital. **Every month** each player chooses the product level (cheap, standard or premium), the price, the volume to produce or buy, advertising in three channels aimed at three customer groups (for example students, workers and families), the team size (hiring and severance cost money, new staff are inexperienced), investments (capacity, training, delivery, card payments, a loyalty CRM, renovation, a business-specific upgrade, a second branch from month 4, market research) and loans. The market model has three customer groups with their own size, seasonality and sensitivity to price, quality, reputation and convenience. Advertising builds awareness (20% of people forget you each month, each extra million reaches fewer new people), regulars come back when they are satisfied and leave after sharp price rises, and many of the customers a business cannot serve go to the rival. From month 2 each month brings one of 27 situations (18 ask for a decision, 9 hit both businesses), and some decisions pay off months later (insurance → fire, permit → inspection, official payroll → tax audit, an investor’s money → a share of the final result). Rules: 4% turnover tax, 12% social tax on official payroll, 2% monthly interest, an emergency loan with a 10% fee when cash runs out, bankruptcy above 150 mln debt. Whoever has more money of their own after month 12 (cash − debt + assets + stock, minus the investor’s share) wins. The decision screen shows a live forecast (expected profit, demand range, break-even point), a cash plan with a one-click loan when money is short, an advisor tip, and on every investment card its forecast monthly gain and payback time. Each month ends with a report: who each customer group bought from, profit-and-loss and cash-flow tabs, notes, customer reviews, the rival’s moves and the lesson of the situation linked to its course topic. The final screen shows the verdict and the player’s strategy, a month-by-month money chart, a side-by-side comparison, badges and personal lessons drawn from the player’s own decisions. Play against four bots — Careful Anvar (easy), Bargain Bobur and Quality Dilnoza (medium), Strategist Jasur (hard); progress is saved in the browser — or a classmate: open a room and share the 4-character code (the host may switch the business while waiting), join by code, or invite from the online list. Classmate games use the original arena database (`arena/biz/<code>`: `meta` with version, business and seed, `p` players, `d/m0/<player>` business plans, `d/m<month>/<player>` decisions, `s` heartbeats; invites in `arena/binv`, which the original arena does not read; rooms older than a day are removed through `arena/bizidx`; rooms from the first version of the game are not opened). Each player writes only their own plan and decisions; the engine (`lib/biznes.ts`) is deterministic and uses no `Math.exp`/`Math.pow`, so both browsers compute exactly the same months from the seed. The business plan has a 4-minute timer and each month a 3-minute timer (the current choices are sent when it runs out); if the classmate disconnects, the other player may let a bot make their plan and moves. Results do not change the ranking — it is practice.

## Architecture

```text
app/                 Next.js App Router, layout, HTTP API
components/          Dashboard, viewer, quizzes, staff tools, auth, games
components/ui/       Reusable shadcn-style Button
lib/server/          Authentication, authorization, validation, repository, rewards
lib/                 Types, original catalog, seed content, translations
scripts/             Preserve/copy original site; administrator bootstrap
public/              PWA assets; generated legacy presentation copy
tests/               Domain tests, Firestore rules, browser journeys
docs/                Data model, implementation, deployment
```

The client uses hash navigation within the root App Router page. Sensitive actions go through protected Node.js route handlers. Firebase Admin credentials stay on the server. Client Firestore and Storage rules deny all private reads and writes; the HTTP API verifies identity, role, enrollment, and original account ownership before using Admin SDK access.

`scripts/sync-legacy.mjs` generates the catalog and copies original materials into `public/legacy/` before development/build. Only the generated copy receives the same-origin interaction adapter and local demo guard. The visible content is sanitized and rendered in the main document using the new design; an offscreen compatibility engine preserves original assessment and game rules. See [native design migration](docs/NATIVE-DESIGN.md). Edit original lessons in the repository root and the shared engine in `_reyting-manba/`, then run `python3 _reyting-manba/inject.py` from the repository root. Do not edit generated copies.

```bash
npx playwright install --with-deps chromium

```

Browser tests launch a local demo server and cover responsive navigation, languages, theme persistence, role escalation rejection, lesson completion and duplicate rewards, preservation of the original viewer, and staff controls. Firebase rules tests use only the `demo-studyquest` emulator project. No live database credentials are required for these tests.

It checks the direct Google button, blocked popup feedback, saved Google sessions, expired/revoked session recovery, and original code sign-in with preserved academic points. It never contacts live authentication or modifies student records.

## Production setup and current boundaries

See [deployment instructions](docs/DEPLOYMENT.md), [database schema](docs/SCHEMA.md), and the [preservation plan](docs/IMPLEMENTATION.md). Recommended hosting is **Vercel + Firebase**, with Vercel's root directory set to `studyquest`. Existing GitHub Pages links now redirect to the corresponding course, topic or game in the new environment.

This implementation is ready for a configured staging review. Real Firebase sign-in, Storage, and production deployment need your Firebase/Vercel setup; local tests do not prove those external integrations are configured.

- Points shown in the rankings are the original academic points (presentations + teacher marks + live-quiz prizes). New-platform lessons and quizzes record completion and results but award no separate XP.
- The daily ranking starts counting once a student opens a presentation with the current engine that day; students on an older cached copy show 0 until they reload.
- Lesson completion requires at least 80% unique slides and the configured server-measured elapsed time. This checks coverage/time, not learner attention.
- **Firestore free quota (50,000 reads/day):** the 15 original presentations never touch Firestore — opening one and turning slides used to cost about 15 + 5 reads per slide, and their reading history and points already live in the original database. Leaving a presentation refreshes only the student's original academic record (`view=me`), not the whole state. Original-presentation students do not load their redundant Firestore progress while the catalog has only original presentations. The catalog (courses, lessons, quizzes) is cached for 6 hours per server instance and refreshed within 30 seconds of a teacher's change through `meta/catalogVersion`. The class-wide report (all students' progress) loads only when a teacher presses «Load the report».
- Starting a quiz consumes an attempt. Refreshing an in-progress new quiz does not restore its unsent answers. Short answers use teacher-defined accepted variants, not AI grading. Publish quiz edits between assessment sessions.
- Collection reads fetch successive 500-document pages, so migrated student records are not silently truncated. Before opening a large paid service, replace broad report scans with scoped queries and materialized leaderboard aggregates. Index definitions are included.
- Original learning content remains Uzbek. Interface navigation and key learning flows support three languages; teacher-created content and the small practice activities retain their authored language.
- Uploads currently support PDF, PNG, and JPEG up to 4 MiB. Uploaded files download through an authorized API; original PDFs/video remain in their existing presentation viewer.
- Practice mini-games are local exercises and award no points. Live multiplayer Quiz Battle uses the existing arena rather than a new matchmaking service. Top Student badges are teacher-approved.
- Payments, subscriptions, marketplace checkout, push delivery, arbitrary file formats, and offline lesson synchronization are future integrations. No billing or purchases are simulated.
- Original static lesson files remain publicly addressable, as on the existing website. Future paid materials should use the protected API and Storage, rather than public legacy HTML files.

In managed environments that proxy HTTP, run local browser checks with
`NO_PROXY=127.0.0.1,localhost no_proxy=127.0.0.1,localhost` for loopback traffic.
Keep the configured HTTPS proxy and CA trust for external destinations.
